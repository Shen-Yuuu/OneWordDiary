# 分享备注状态直连修复设计

## 目标

修复“展示备注”开关已经切换，但单日与最近七日分享卡片不显示备注的问题。背景与图片导出流程保持现状。

## 现象与根因

- 设备日志证明 `Toggle.onChange` 正常执行，页面的 `showNote` 已从 `false` 更新为 `true`。
- 页面下方状态文案也会随 `showNote` 更新，说明父组件状态管理正常。
- 当前工作区同时存在普通 `@Prop` 传值、`refreshKey/.key()` 强制重建和未使用的 `ShareCardData` 三种刷新尝试，状态链没有形成单一来源。
- `refreshKey/.key()` 仅覆盖单日卡片，并在切换后强制销毁、重建整棵卡片子树。设备随后连续报告 `JSText::SetTextColor ParseJsColor failed!` 和卡顿，说明该重建补丁引入了不稳定的中间渲染状态。
- 先前单日闪退来自备注值为 `undefined` 时读取 `.length`；`resolveShareNoteText` 当前已接受 `null | undefined` 并保证返回字符串，因此该风险已经独立消除。

## 方案比较

### 方案 A：使用 `@Link` 直连开关状态（采用）

父页面持有唯一的 `@State showNote`，通过 `$showNote` 同时传给 `ShareSingleCard` 和 `ShareScrollCard`。两个卡片以 `@Link includeNote` 观察同一个状态。

- 单日卡片接收原始 `note`，在组件内用安全函数解析最终显示文本。
- 七日卡片在 `includeNote` 变化后重新计算高度和展示数据，`ForEach` key 包含备注开关状态，使记录节点按新数据重建。
- 删除 `refreshKey/.key()` 以及未使用的 `ShareCardData` 引入，避免强制销毁整张卡片。

优点：改动范围小、状态来源唯一、与项目现有 V1 状态管理一致，并且预览和导出天然使用同一状态。

### 方案 B：父页面维护完整的可观察分享数据对象

每次切换开关时，由父页面重新生成单日对象和七日数组，再通过 `@ObjectLink` 传递。

优点是数据快照明确；缺点是为一个布尔开关引入额外模型、同步和数组复制，复杂度明显更高。

### 方案 C：迁移分享组件到状态管理 V2

使用 `@ComponentV2/@Param/@Event` 重写分享组件。

长期语义更清晰，但会扩大改动面，不适合本次定点回归修复。

## 数据流

`Toggle.onChange` → `SharePreviewPage.@State showNote` → `$showNote` → 两个卡片的 `@Link includeNote` → 安全解析备注 → 条件布局与文本 → 同一卡片节点快照导出。

## 诊断日志

保留少量隐私安全日志：

- 页面：模式、切换前后布尔值。
- 单日卡片：`includeNote`、备注长度、最终展示文本长度。
- 七日卡片：`includeNote`、总天数、可展示备注的记录数。

不记录备注正文。

## 验证

- 单日有备注、无备注、正式留白三种记录，开关打开后分别显示真实备注或兜底文案，关闭后隐藏。
- 最近七日的已有记录显示备注或兜底文案，缺失日期不显示备注；卡片高度同步变化。
- 单日与七日导出图片和屏幕预览一致。
- 快速来回切换不崩溃，不再因 `refreshKey` 触发批量颜色解析失败。
- ArkTS 编译及现有测试通过。

## 非目标

- 不再调整分享背景、纸张纹理或图片合成流程。
- 不改变备注文案规则和分享卡片视觉样式。

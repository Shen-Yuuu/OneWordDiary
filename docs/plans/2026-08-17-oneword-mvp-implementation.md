# 一字日记：1.0 实施计划

- 日期：2026-08-17
- 对应方案：[2026-08-14-oneword-mvp-design.md](./2026-08-14-oneword-mvp-design.md)
- 工程目录：`OneWord_dev/`
- 基线：HarmonyOS 6.0.1 / API 21 / Stage 模型 / 手机
- 状态：节点 0 已完成，准备进入节点 1；当前没有必须等待用户补充的阻塞项

## 1. 实施目标

交付一个完全离线、可在 HarmonyOS 手机上运行的 1.0：

- 用户可以写下 1–4 个用户感知字符或选择留白。
- 首次提交后，在固定截止时间前只有一次修订机会。
- 用户可以回看文字长卷和单日详情。
- 用户可以设置本地提醒、生成单日/7 日分享图。
- 用户可以主动导出和安全导入基础备份。
- 应用不联网、不统计、不自动备份私人数据。

预计单人开发为 **14–19 个工作日**；种子验证另需至少 7 个自然日。估算包含开发素材，不包含最终商用字体、图标制作和商店审核等待。

## 2. 当前工程状态

`OneWord_dev/` 已是可用的 HarmonyOS Stage 模板，不需要重新建项目。

已确认配置：

- `targetSdkVersion`：`6.0.1(21)`
- `compatibleSdkVersion`：`6.0.1(21)`
- `deviceTypes`：仅 `phone`
- `bundleName`：模板值 `com.example.oneword`
- 首页：默认 `Hello World` 页面
- 测试：已有 Hypium 和 Hamock 模板
- 签名：尚未配置，不影响本地开发
- 系统备份：模板默认存在 `EntryBackupAbility`，且 `allowToBackupRestore=true`

开始业务开发时，将开发期 `bundleName` 改为 `com.oneword.diary`，应用显示名改为“一字日记 / OneWord Diary”。首次外部分发前必须确认最终 `bundleName` 可用，因为上架后不能更换。

## 3. 实施顺序

### 节点 0：工程基线与隐私边界

预计：1 天。

工作：

- 更新应用名、描述、版本信息和开发期 `bundleName`。
- 移除默认演示页面、演示测试和无用资源。
- 移除 `EntryBackupAbility` 及其配置，或将系统备份明确关闭。
- 确认 `module.json5` 只声明必要能力，不申请网络权限。
- 建立 `pages/components/model/viewmodel/service/repository/utils/constants` 目录。
- 加入开发版颜色、尺寸、两套风格 token 和可替换资源命名。
- 建立应用级错误类型和日志规则，禁止记录正文与注解。

完成条件：

- Debug 构建成功并可在手机模拟器启动。
- 首页显示开发版“一字”空壳，不再显示模板内容。
- 配置中没有网络权限和系统自动备份能力。
- 工程只有一个 `entry` 模块。

### 节点 1：领域规则与本地数据

预计：2–3 天。后续所有页面依赖本节点。

工作：

- 定义 `DailyRecord`、`RecordType`、`StylePreset`、`ReminderSettings` 等严格类型。
- 实现 grapheme 规范化、计数和输入校验。
- 提供可替换的 `Clock`，业务代码不能直接散落调用系统当前时间。
- 实现本地日期、时区 offset 和 `revision_deadline_at` 计算。
- 创建 RDB、`daily_record` 表、唯一主键和 schema 迁移入口。
- 创建 `DiaryRepository`、`SettingsRepository`。
- 创建 `DiaryService`，封装首次提交、留白、修订、查询资格和清空规则。
- 首次提交和修订都放在事务中，处理快速重复调用。

完成条件：

- Emoji、ZWJ、肤色修饰、组合字符和中文输入的测试通过。
- 23:58、23:59、跨日、时区变化和时间回拨场景有固定时钟测试。
- 同一日期并发提交只生成一条记录。
- 修订写入失败或取消时不消耗次数。
- 进程重启后可以完全从 RDB 恢复状态。

### 节点 2：今日记录闭环

预计：2–3 天。

工作：

- 构建唯一首页和今日状态 ViewModel。
- 完成日期、灵感、正文输入、字符反馈、折叠注解和风格预览。
- 完成“落字 → 确认 → 收入长卷”的双确认流程。
- 完成“把今天留给空白”流程。
- 完成已提交卡片、剩余修订提示和永久定稿流程。
- 增加写入中禁用、防重复触发、失败反馈和进程恢复。
- 实现短定格动效、轻触反馈以及减少动效替代方案。

完成条件：

- 冷启动到提交不超过 3 次主要点击。
- 写字、留白、写字转留白、留白转写字均通过。
- 退出确认页、切后台和杀进程不会误提交或误消耗修订。
- 大字号和屏幕朗读可完成全部流程。

### 节点 3：文字长卷与详情

预计：1.5–2 天。

工作：

- 按日期倒序读取记录，使用虚拟化列表和稳定 key。
- 构建月份分段、正文节点、留白节点和空状态。
- 点击节点进入单日详情。
- 详情展示日期、正文或留白、注解和提交风格。
- 显示“已留下 N 天”，写字与留白都计入。
- 为未来分页和月份查询保留 Repository 接口，但 1.0 不增加日历模式。

完成条件：

- 365 条以上记录滚动稳定，无明显卡顿或组件爆量。
- 历史记录不随当前风格切换而改变。
- 缺失记录和正式留白在 UI 与朗读语义上明确不同。

### 节点 4：设置、风格与本地提醒

预计：1.5–2 天。

工作：

- 提供 `paper_ink` 和 `plain_ash` 两套完整预设。
- 风格切换只影响新记录和当前预览。
- 提供提醒开关和时间选择。
- 用户开启提醒时再请求通知权限。
- 处理拒绝、系统关闭、调度失败、修改时间、关闭提醒和设备重启。
- 提供隐私说明入口和“清空全部数据”两步确认。
- 清空后删除 RDB 数据、重置设置并取消提醒。

完成条件：

- 未主动开启提醒时不申请通知权限。
- 权限拒绝不会反复弹窗，设置页有解释和系统入口。
- 清空失败时不留下半清空状态；成功后回到首次使用状态。

### 节点 5：分享图片

预计：2 天。

工作：

- 实现独立 `ShareCardRenderer`，不从页面截图拼接。
- 支持单日卡和最近 7 日微型长卷。
- 两类分享图默认都不包含注解。
- 提供固定分享预览，确认后调用系统分享面板。
- 适配两套风格、不同密度和大字号。
- 临时图片写入应用缓存，完成或超时后清理。

完成条件：

- 分享图与预览一致，不截断、不拉伸。
- 不包含隐藏标识、日记注解或分析数据。
- 分享取消、目标应用失败或存储异常不影响原始日记。
- 缓存中没有长期遗留的分享图片。

### 节点 6：基础备份与恢复

预计：2 天。

工作：

- 定义 `.oneword` 格式和 `format_version=1`。
- 导出记录和风格设置，不导出设备通知权限。
- 导出前提示文件未加密且包含私人记录。
- 通过系统文件选择能力让用户主动决定位置。
- 导入时先解析到内存模型并完成全量预检。
- 冲突日期保留本机记录，只导入缺失日期。
- 所有导入写入在同一事务中完成。
- 完成后报告导入数、跳过冲突数和错误原因。

完成条件：

- 损坏 JSON、未知版本、非法日期、超长字符和重复记录都不能改变本机数据。
- 中途失败时事务回滚。
- 导出再导入可还原记录内容、时间字段和历史风格。
- 大文件有数量或大小上限，不造成明显卡死或内存失控。

### 节点 7：整体验收与加固

预计：2–3 天。

工作：

- 补全领域单测、Repository 集成测试和关键 UI 流程测试。
- 执行时间边界、并发提交、进程恢复、权限拒绝和异常文件测试。
- 检查深浅系统模式、常见手机宽度、屏幕密度和大字号。
- 检查屏幕朗读、点击区域、颜色对比和减少动效。
- 检查启动时间、长卷滚动、分享渲染和 RDB 查询。
- 扫描权限、依赖、日志和缓存，验证无网络请求、无敏感日志、无自动备份。
- 使用开发版素材完成可替换资源清单。

完成条件：

- 产品方案第 15 节全部验收项通过或有明确缺陷记录。
- 没有阻断记录、修订、恢复和数据安全的高优先级问题。
- 生成可安装的 Debug 测试包。

### 节点 8：种子验证与发布准备

开发修复预计：1–2 天；观察期至少 7 个自然日。

工作：

- 邀请 10–20 名种子用户，不收集或要求上传日记正文。
- 在 D1、D3、D7 询问打开意愿、7 日长卷价值和规则压力。
- 修复阻断和高频理解问题，不在测试中临时增加大功能。
- 替换最终授权素材，补齐隐私文案、反馈邮箱、签名和发布配置。
- 最后确认应用名和 `bundleName`，生成 Release 包。

完成条件：

- D7 反馈能够回答“是否仍愿意记录”和“积累是否有价值”。
- Release 构建、安装、升级和卸载重装路径完成测试。
- 签名、版本号、隐私说明和素材授权齐全。

## 4. 测试重点

| 层级 | 必测内容 |
| --- | --- |
| 领域单测 | grapheme、NFC、日期截止、时区、状态转换、一次修订 |
| 数据测试 | 唯一主键、事务回滚、迁移、并发提交、分页查询 |
| UI 测试 | 写字、留白、修订、长卷、清空、进程恢复 |
| 系统测试 | 通知授权与投递、系统分享、文件导入导出、重启 |
| 可访问性 | 大字号、屏幕朗读、减少动效、触控区域、对比度 |
| 隐私检查 | 无网络权限、无自动备份、无正文日志、缓存清理 |

时间相关测试全部使用可控时钟，不通过等待真实时间完成。分享、提醒、系统文件选择器和重启行为必须在至少一台真机上复测，模拟器结果不能替代。

## 5. 开发过程中真正需要的前置内容

当前已经具备：

- 已确认的 1.0 范围和规则。
- 可用的 Stage 手机工程。
- API 21 开发基线。
- 使用可替换开发素材的授权。
- 签名后补、不阻塞 Debug 开发的确认。

因此可以直接开始节点 0，不需要后端、域名、云数据库、账号系统、分析平台、IAP 或 AI 服务。

在对应阶段到来前，只需要补齐以下内容：

1. **真机测试条件**：最晚在节点 4 前提供一台 API 21 兼容手机，用于通知、分享、文件选择和重启测试。
2. **最终应用标识**：最晚在首次对外发包前确认 `bundleName` 唯一，并填写实际 vendor。
3. **发布素材**：最晚在节点 8 前提供或确认最终图标、字体、纸张纹理和灵感文案的商用授权。
4. **发布信息**：节点 8 前提供签名、发布账号、反馈邮箱和最终隐私说明。

除此之外，不需要为了“以后可能使用”提前准备任何平台或服务。

## 6. 执行约束

- 产品方案是需求唯一来源；发现冲突时先修订方案，再改代码。
- 每个节点完成后先运行相关测试，再进入依赖它的下一个节点。
- 不提前实现后续版本能力。
- 不为 1.0 拆分多模块、引入通用框架或搭建网络层。
- 任何可能导致日记丢失的操作都必须有事务、预检或可恢复路径。
- 用户正文和注解不得进入日志、崩溃信息、分享元数据或测试夹具。
